# Готовые промпты

Для Claude Code / Codex в этом репозитории. Контекст проекта они берут из
`AGENTS.md` / `CLAUDE.md`, поэтому промпты короткие. Подставь значения в `<…>`.

## 1. Интегрировать новый фид

```
Интегрируй фид <название> (<homepage>, docs: <url>) как adapters/feeds/<id>.
Следуй скиллу /add-feed. Сначала заполни карточку фида (объект оценки, шкала
как опубликована + ссылка на методологию, доступ/ключ/лимиты, фильтр Ethereum,
их id для наших протоколов, частота обновления) и покажи её мне до кода.
Маппинг делай только для протоколов из registry/protocols.json; то, что не
удалось сопоставить однозначно, вынеси списком с вопросами, не угадывай.
Значения verbatim, никаких шкал и цветов от нас. Списки в extra ограничь 100.
Прогони npm run collect -- --source <id> --verbose, покажи data/protocols/<protocol>.json
для одного покрытого протокола, добавь тест на урезанном реальном ответе,
обнови README/.env.example/refresh-data.yml, запусти полный набор проверок
и приведи вывод тестов дословно.
```

## 2. Выполнить пункт плана из отчёта

```
Открой docs/refactoring-report.md и выполни пункт <A2> (раздел 4, «что сделать»).
Ограничения: без новых зависимостей (кроме тех, что названы в пункте), минимальный
диф, существующие тесты зелёные, поведение из CHARTER.md не меняется. Если пункт
требует изменить формат data/protocols/*.json — скажи об этом до правок и
предложи, как переходный период переживёт carry() старых записей. В конце:
полный набор проверок (lint, format:check, typecheck, test, build) и обновлённые
места документации (adapters/README.md, _template, скилл add-feed), если
изменилось API адаптера.
```

## 3. Ревью адаптера по чартеру

```
Сделай ревью adapters/feeds/<id>/ как ревьюер, который отвечает за CHARTER.md.
Проверь по пунктам и приведи строки кода: (1) value — строка ровно как опубликовано,
без округления/конверсии/наших ярлыков; (2) null только для «не покрыт», throw только
для «не смогли прочитать», «в списке, но без оценки» → note без value; (3) updatedAt —
дата фида, не наша, sentinel-даты отброшены; (4) url ведёт на страницу фида про этот
протокол; (5) note описывает охват и исключения, не выносит суждений; (6) ничего не
считается поверх нескольких объектов так, чтобы это читалось как оценка протокола
(счётчики покрытия — можно); (7) extra использует только поля из types.ts и схемы,
списки ограничены; (8) сеть только через ctx, ключи не минтятся при чтении из кэша;
(9) mapping.json: все ключи есть в registry/protocols.json. Отдельно: что в выводе
адаптера станет шумом в git-истории data-репозитория (значения, меняющиеся каждый
прогон без смысловых изменений).
```

## 4. Добавить протокол в реестр

```
Добавь протокол <название> (версия <v>, сайт <url>) в registry/protocols.json
(id в стиле существующих, group если есть другие версии, category из используемых).
Затем пройди по всем adapters/feeds/*/mapping.json и adapters/metrics/tvl/mapping.json:
для каждого фида найди в его источнике идентификатор этого протокола и добавь строку;
где не нашёл — не добавляй, а перечисли мне с ссылками, где искал. DefiLlama id
проверь через https://api.llama.fi/lite/protocols2 (поле defillamaId, Ethereum TVL).
Прогони npm run collect -- --protocol <id> --verbose и покажи флаги и запись.
```

## 5. Анализ нового фида до интеграции (без кода)

```
Изучи фид <название> (<url>) и ответь по карточке из скилла add-feed, шаг 0,
со ссылками на их документацию по каждому пункту. Дополнительно: пересечение с
нашим реестром протоколов (таблица «наш id → их id → уверенность»), есть ли
машиночитаемый доступ и на каких условиях, публикует ли фид порядковую шкалу и
где она описана, лицензия/условия цитирования. Кода не пиши. Если чего-то не
нашёл — так и скажи, не додумывай.
```
