## 1. Коротко

**Большой рефакторинг не нужен.** Кодовая база маленькая (4 872 строки TS/TSX без мокапов) и устроена правильно: папка = адаптер, один контракт `Adapter<Result>`, никакого центрального списка фидов, фронтенд подхватывает новый фид через `import.meta.glob`. Это уже та архитектура, которую обычно получают _после_ рефакторинга.

Что реально мешает писать адаптеры и поддерживать код — это десяток точечных вещей, каждая на 10–60 строк. Суммарно 3–5 рабочих дней, одна новая зависимость максимум (`ajv`, и та опциональна). Список и порядок — в §5.

**База данных сейчас не нужна** и не понадобится в горизонте гранта. Данные обновляются дважды в сутки одним писателем, читаются как статика, их объём — 476 КБ на снимок. Всё, что могло бы потребовать БД (история, запросы, несколько писателей), либо не требуется, либо решается без сервера. Если потребность появится, порядок такой: append-only NDJSON-лог в git → SQLite как build-артефакт для запросов в браузере → Postgres с `jsonb` только когда появится бэкенд по другой причине. Разбор — в §6.

**Один срочный пункт вне рефакторинга:** `grant_data/` лежит внутри дерева публичного AGPL-репозитория, не в `.gitignore`, содержит вложенные `.git`, подписанные PDF и приватный due diligence. Один `git add -A` — и это уходит в публичный репозиторий. Исправление — две строки (B1).

## 3. Что уже хорошо — не трогать

- **Папка = источник.** `adapters/feeds/<id>/{feed.json, mapping.json, index.ts}`; `registry.ts:44-63` загружает папки, сверяет `id` с именем, пропускает `_`-шаблоны. Фронт делает то же через `import.meta.glob` (`apps/web/src/lib/registry.ts:24-30`). Нигде нет списка фидов, который нужно синхронизировать.
- **Контракт адаптера.** `prepare()` раз в прогон, `collect()` на протокол, `null` = «не покрыт», `throw` = «не смогли прочитать». Это ровно то различие, на котором стоит CHARTER §3, и оно закреплено в `collect.ts:99-129`.
- **HTTP-слой.** Кэш на диске с TTL, `--offline`, ретраи, ожидание 429, fallback на старую копию при сетевой ошибке, `headers` как функция (токен не минтится при чтении из кэша). Адаптеры не трогают `fetch`.
- **Перенос прошлых значений** при ошибке и при частичном прогоне (`carry()`), changelog как diff значений.
- **Разделение ручного и сгенерированного.** Реестр и `feed.json` компилируются в сайт; данные читаются в рантайме по `config.json` — сайт деплоится без данных и наоборот.
- **Документация** (`adapters/README.md`, `_template/README.md`, схемы с описаниями полей) — выше среднего. Комментарии в коде объясняют _почему_, не _что_.
- **Инструментарий:** strict TS, ESLint 10 + Prettier, husky + lint-staged, CI с полным набором проверок, Node 24, `tsx`, `with { type: 'json' }`. Ничего менять не нужно.

Отдельно: архитектурный документ гранта (`openrisk_final_architecture.md`) описывает более тяжёлую систему (scope как первичный ключ, NDJSON-лог, tone policy, charter-тесты, Astro). Реализованный проект — его осознанно упрощённая версия, и это правильный выбор для 280 часов бюджета. Из того документа стоит взять только три вещи, и они ниже: коммит только при реальном изменении (B2), машиночитаемый scope фида (A10), тесты на фикстурах (A5).

## 4. Находки

Формат: что · где · чем мешает · что сделать · объём. Приоритеты сведены в §5.

### 4.1 Написание и интеграция адаптеров (цель 2)

**A1. Один и тот же код маппинга скопирован в шесть адаптеров, а ключи маппинга никто не проверяет.**

- Где: `_template/index.ts:13-17`, `philidor/index.ts:18-22`, `pigi/index.ts:24-28`, `metrics/tvl/index.ts:7-11`, `metrics/incidents/index.ts:8-12`, вариация в `defiscan/index.ts:24,86-88`.
- Чем мешает: пять строк шаблонного кода в каждом адаптере; опечатка в ключе `mapping.json` (`"aave-v3 "` или `"aave_v3"`) молча превращается в серую ячейку «нет данных» — а это именно та ошибка, которую чартер считает недопустимой (пробел выглядит как факт о покрытии).
- Что сделать: `registry.ts` читает `mapping.json` рядом с адаптером (если есть), нормализует значения в `string[]`, **проверяет, что каждый ключ есть в `registry/protocols.json`** (иначе ошибка при старте), и отдаёт адаптеру как `ctx.mapping: Record<string, string[]>`. Адаптер пишет `const ids = ctx.mapping[protocol.id] ?? []`, а в `prepare` — `Object.values(ctx.mapping).flat()`. Импорт `mapping.json` из `index.ts` исчезает. `incidents` может оставить свой импорт из `../tvl/mapping.json` — это нормально.
- Объём: ~25 строк в core, −5 строк в каждом адаптере.

**A2. `prepared: unknown` и ритуал «listing unavailable».**

- Где: `philidor/index.ts:104-105`, `pigi/index.ts:191-192`, `tvl/index.ts:45-46`, `incidents/index.ts:49-50`; раннер `collect.ts:59-66, 82-129`.
- Чем мешает: каждый адаптер делает `prepared as Map<…> | undefined` и `if (!listing) throw`. Когда `prepare()` падает (например, нет `PIGI_API_KEY`), раннер всё равно вызывает `collect()` для всех 26 протоколов, и в отчёте появляется 1 + 26 строк `failed:`. Шум и лишний код.
- Что сделать: (а) сделать тип обобщённым — `Adapter<Result, Prepared = void>` с `prepare?(ctx): Promise<Prepared>` и `collect({ prepared: Prepared })`, тогда касты не нужны; (б) если `prepare()` упал, раннер не вызывает `collect()` для этого адаптера, а сразу помечает его колонку как `error` с переносом прошлых значений — одна строка в `failures`.
- Объём: ~15 строк в `types.ts` и `collect.ts`, −2 строки в каждом адаптере.

**A3. `extra` типизирован по фидам, а не по формам отображения. Это главный тормоз для новых фидов.**

- Где: `types.ts:106-125` (`philidorId`, `vaultsLive`, `domain`, `riskLevel`…), `FeedExtras.tsx:7-26, 47-52, 109-116` (три списка ключей вручную), `schemas/protocol-record.schema.json` (те же ключи).
- Чем мешает: фид с новыми структурированными данными требует правок в четырёх местах (тип, схема, компонент, список ключей в `hasFeedExtras`). Ты сам пишешь, что закономерности в данных будущих фидов не видишь — значит, этот путь будет повторяться на каждом фиде.
- Что сделать: оставить в `ExtraData` **только формы, которые умеет рисовать UI**, без имён фидов:
  - `facts?: { name: string; value: string }[]` — пары «метка → значение» (сюда уходят `domain`, `riskLevel`, `overallScore`, `analysisStatus`, `philidorId`, `versions`, `vaultsListed/Live/Shutdown/Rated`);
  - `findings?: ExtraFinding[]` (сейчас `keyFindings`), `reviews?`, `vaults?`, `incidents?`, `components?`, `text?` — уже есть и уже общие.
    Тогда `FeedExtras` — это один компонент на форму, `hasFeedExtras` — `Object.values(extra).some(nonEmpty)`, а новый фид выбирает из каталога форм. Новый компонент нужен только когда появляется **новая форма**, а не новый фид. Адаптеры risklayer и philidor переносят скаляры в `facts` (по 5–8 строк).
    Переходный период: `carry()` может сохранить запись старой формы, если фид упал в первом прогоне после деплоя; фронт должен игнорировать неизвестные ключи (так и будет при обобщённом `hasFeedExtras`).
- Объём: `FeedExtras.tsx` 211 → ~120 строк, схема короче, типы короче. Полдня.

**A4. UI не показывает «сырую запись», хотя CHARTER §2 это обещает.**

- Где: CHARTER.md §2: «The protocol page also shows the raw record behind each card». В `FeedAssessment.tsx` и вообще в `apps/web/src` нет ни `JSON.stringify`, ни `<pre>`.
- Чем мешает: расхождение между уставом и продуктом. И практически: новый фид, у которого `extra` пока не имеет компонента, вообще не виден на странице.
- Что сделать: в `FeedAssessment` внутри «Explore assessment» добавить `<details><summary>Raw record</summary><pre>{JSON.stringify(data, null, 2)}</pre></details>`. Это одновременно fallback для любого нового фида: данные видны с первого дня, красивый компонент — потом.
- Объём: 10 строк + CSS.

**A5. Нет стандартного способа протестировать `collect()`; тестируются только случайно вынесенные чистые функции.**

- Где: `defiscan/index.test.ts` тестирует `parseReview`, `pigi/index.test.ts` — `assess`. У philidor, risklayer, tvl, incidents тестов нет. В core нет `fakeContext`.
- Чем мешает: чтобы написать тест, автор должен сначала придумать, как вынести логику из `collect()`. Golden-тесты (архитектурный документ §5.4) невозможны без подделки `AdapterContext`.
- Что сделать: `packages/core/src/testing.ts` с `fakeContext(responses: Record<string, unknown>, mapping?)`, реализующим `AdapterContext` поверх карты «URL → тело» (бросает понятную ошибку на незнакомый URL). Конвенция: `adapters/feeds/<id>/fixtures/*.json` — урезанные реальные ответы (тело берётся из `.cache/http/<sha>.json`, поле `body`). Тест: `prepare(ctx)` → `collect({protocol, ctx, prepared})` → `toMatchObject` на `value/updatedAt/url/extra`. Три сценария на фид: покрыт; в списке, но без оценки → `note` без `value`; не в списке → `null`.
- Объём: ~40 строк helper + по одному тесту на существующий адаптер (по 30–50 строк). День.

**A6. JSON Schema существует, но ничем не проверяется.**

- Где: `schemas/protocol-record.schema.json`, `adapters/feeds/feed-output.schema.json`; `ajv` в `node_modules` только транзитивно через ESLint.
- Чем мешает: README говорит контрибьюторам «unknown keys are invalid», а на деле раннер сохраняет что угодно. TypeScript ловит большинство ошибок формы, но не `status: ok` без `url`, не `value: ''` (`collect.ts:109` превратит в `none`, но пустая строка попадёт в запись и в changelog как изменение `null → ''`), не формат URL.
- Что сделать (выбрать одно): (а) добавить `ajv` как зависимость pipeline и валидировать каждую `FeedData`/`MetricData` в `collect()` перед записью: невалидно → как `throw` (прошлое значение, строка в `failures`); (б) удалить схемы и честно сказать, что контракт — `types.ts`. Схема как публичный артефакт data-API была в планах гранта (§10.3), поэтому склоняюсь к (а).
- Объём: ~30 строк + зависимость.

**A7. Секреты и обмен ключа на токен — ad hoc.**

- Где: `pigi/index.ts:142-154` — `process.env` внутри адаптера, замыкание с мемоизацией токена и сбросом при ошибке.
- Чем мешает: следующие фиды с ключом (Credora, Xerberus, Zyfai, Pharos — все в приоритетном списке) повторят эти 13 строк. Отсутствующий ключ сейчас проявляется как 27 строк ошибок (см. A2), а не как одна понятная.
- Что сделать: поле `secrets?: string[]` у адаптера (или в `feed.json`); раннер до `prepare()` проверяет наличие и пишет одну строку `pigi: skipped, PIGI_API_KEY is not set`, колонка переносится. Для обмена ключа на bearer — `bearerToken(ctx, { url, body })` в core, возвращающий ту же `headers`-функцию. Но только после второго фида с таким же сценарием — пока pigi один, обобщать рано.
- Объём: 15 строк в раннере; helper — когда появится второй случай.

**A8. `extra.vaults` не ограничен — отсюда 100 КБ на одну запись.**

- Где: `philidor/index.ts:165` (`rated.map`), `pigi/index.ts:111`. `TOP_VAULTS = 10` ограничивает только `details`.
- Чем мешает: `morpho-vaults.json` — 197 строк волтов, 100 КБ; при росте Morpho/Euler и добавлении Credora/Xerberus с волт-уровнем запись легко уйдёт за 300–500 КБ, а в data-репозитории каждый прогон переписывает сотни строк TVL (см. B2).
- Что сделать: `MAX_VAULTS = 100` (по TVL), в `note` — «and N more at the source». Это и есть основной рычаг размера данных, важнее любой БД.
- Объём: 4 строки в двух адаптерах.

**A9. Имена фидов зашиты в прозу интерфейса и README.**

- Где: `MethodologyPage.tsx:17` перечисляет DeFiScan, Philidor, pigi, Risklayer; README, раздел «Sources and contributions».
- Чем мешает: добавление фида — ещё два места, о которых легко забыть. Не баг, но пункт чеклиста.
- Что сделать: не рефакторить; внести в чеклист добавления фида (скилл `add-feed`). Фразу в Methodology можно переписать без имён («one feed grades a protocol, another the vaults inside it») — тогда и чеклист короче.

**A10. Объект оценки фида (протокол / деплоймент / волт / пул / актив) живёт только в тексте `note`.**

- Где: `philidor/index.ts:149-157`, `pigi/index.ts:100-107`, `risklayer/index.ts:107`, UI объясняет это на словах в `MatrixPage.tsx:336-342`.
- Чем мешает: UI не может единообразно подписать «эта карточка про волты, а эта про протокол»; будущие фиды (Credora — активы/рынки/волты, Zyfai — пулы, Pharos — стейблкоины, yRisk — документы без шкалы) усугубят разнобой.
- Что сделать: поле в `feed.json`: `"assesses": "protocol" | "deployment" | "vault" | "pool" | "asset" | "research"`, тип в `Feed`, одна подпись в `FeedAssessment` и в карточке на `/sources`. Статично, одно значение на фид, никаких шкал и тонов (CHARTER не нарушается).
- Объём: 15 строк.

### 4.2 Поддержка и риски (цель 1)

**B1. `grant_data/` внутри публичного репозитория — не в `.gitignore` и не в ignore ESLint.** _Срочно._

- Факты: `git status` показывает `?? grant_data/`; внутри `ef-grant-openrisk/.git`, `openrisk-test/`, подписанные PDF, `openrisk-internal/benchmarks/lido/` (помечено «не публиковать»). `npm run lint` падает на 12 ошибках из `grant_data/openrisk-internal/mockups/...`. CI зелёный только потому, что папка не закоммичена.
- Что сделать: либо вынести папку из дерева (лучше), либо добавить `grant_data/` в `.gitignore` и в `ignores` в `eslint.config.js`. Заодно решить судьбу незакоммиченного `.github/dependabot.yml`.
- Объём: 2 строки.

**B2. Каждый прогон коммитит все файлы — история data-репозитория не читается как changelog.**

- Факты (GitHub API, три последних коммита): 27–28 файлов в каждом; у протокола без единого изменения значения — 7–9 изменённых строк (`generatedAt`, `fetchedAt` на каждый фид и метрику); `morpho-vaults.json` — 276–860 строк на прогон из-за движения TVL волтов. Причина: `collect.ts:38,74,90,109` проставляют `fetchedAt`/`generatedAt` на каждом прогоне.
- Чем мешает: CHARTER §4 обещает «every change to every cell is in the git history» — технически так, но найти изменение среди шума нельзя. Рост репозитория: ~2 коммита/день × ~1–2 тыс. строк диффа.
- Что сделать: разнести «что фид опубликовал» и «когда мы читали». Записи содержат только контент (значения, `updatedAt` фида, `url`, `extra`); времена последнего успешного чтения — в отдельном маленьком `data/status.json` `{feedId → {lastRunAt, lastOkAt}}` (его дифф — одна строка на фид). Workflow коммитит только если изменился хотя бы один файл кроме `status.json` — тогда коммит = реальное изменение данных, а git log = changelog. ### 4.3 Чего не делать (цель 3)

Перечисляю явно, потому что каждое из этого выглядит «правильным» и каждое — лишнее при 4 фидах и 26 протоколах:

- **Не вводить Zod/valibot для всего.** Типы + одна JSON Schema на выходе — достаточно. Zod имеет смысл только если схема будет генерироваться из него, а это ещё одна система.
- **Не делать базовых классов / фреймворка адаптеров** (`ApiAdapter`, `GitAdapter`, `ManualAdapter`). Четыре адаптера уже показали, что общего между ними — только контракт и `ctx`. Пагинация у philidor (page/totalPages) и pigi (offset/hasMore) разная — общий `paginate()` будет сложнее двух циклов.

- **Не добавлять turborepo/nx/changesets.** Три workspace-пакета, npm workspaces справляются.
- **Не дробить `collect.ts`** на модули ради размера — 200 строк с комментариями читаются целиком.
- **Не добавлять scope как отдельную сущность** (архитектурный документ §3.1): «протокол-версия = строка» уже решает задачу; инстансы (`aave/prime.md`) живут в `extra.reviews`.
- **Не вводить БД** — §6.
- **Не писать Playwright-скрейпинг** вердиктов — запрещено политикой источников и чартером.

### 6.5 Нужна ли БД сейчас — нет

1. **Требования гранта и команды.** `decisions.md` 2026-09-16: «Базы данных на гранте не делаем (минимум 6 месяцев)». Архитектурный документ §10–11, §16: «сервера нет, базы нет». EF на звонке 05.08 просил статический хостинг / IPFS и нулевые эксплуатационные расходы после гранта. Любая СУБД с сервером противоречит всем трём.
2. **Аудируемость.** Git-история data-репозитория — и есть требуемый RFP audit trail; СУБД его либо дублирует, либо заменяет на что-то менее проверяемое снаружи.
3. **Форки.** Форк репозитория собирается без ключей и без инфраструктуры — важное свойство AGPL-проекта. С БД форк превращается в «разверни Postgres».
4. **Гетерогенность.** Разнородный `extra` — аргумент _за_ документное хранение, которое у нас уже есть (JSON), а не за реляционную схему.
5. **Объём.** §6.3: мегабайты, не гигабайты; одна запись на прогон, не поток.

### 6.8 Рекомендация-лестница

0. **Сейчас (и весь грант):** JSON в git. Сделать B2 (коммит только при изменении, `status.json`) и A8 (кап списков) — это даёт читаемую историю и держит объём, то есть закрывает 80 % того, зачем люди заводят БД «для истории».
1. **Когда потребуется страница истории:** добавить `observations/<feed>/<YYYY-MM>.ndjson` (одна строка = `{ts, protocolId, feedId, status, value, updatedAt, url, hash}`; пишется, когда `hash` изменился). `bundle` сворачивает лог в текущие записи — или наоборот, лог выводится из diff записей, как сейчас changelog. Ноль серверов, формат текстовый, git-дружелюбный.
2. **Когда потребуются запросы (публичный API с фильтрами, «все волты тира B у всех фидов»):** `bundle` дополнительно собирает `data.sqlite` (таблицы `protocols, feeds, runs, observations(feed_id, protocol_id, run_id, status, value, updated_at, url, payload JSON)`) и публикует его как артефакт рядом с сайтом; фронт читает через `@sqlite.org/sqlite-wasm` с range-запросами. Файл не коммитится (бинарный), пересобирается из NDJSON. Всё ещё без сервера.
3. **Только если появится бэкенд по другой причине** (аккаунты, формы, платные API, подписки): Postgres с той же схемой, `payload jsonb`, Drizzle; Supabase/PostgREST снимает написание API. Сайт продолжает читать статический экспорт — статический хостинг и форки не ломаются.

Схема для шага 2/3 одна и та же, и она прямо соответствует текущим типам (`FeedData` → `observations`, `Feed` → `feeds`, `Protocol` → `protocols`), так что миграция — это `INSERT` из JSON, не редизайн.

### 6.9 Что сделать в JSON-слое уже сейчас, чтобы любой из шагов был дёшев

- Стабильный конверт записи (есть) + `extra` по формам (A3) — тогда `payload jsonb` будет однородным.
- Коммит по изменению (B2) — тогда NDJSON-лог выводится из git-истории механически, если понадобится задним числом.
- `assesses` у фида (A10) — поле, по которому потом строятся фильтры.
- Кап списков (A8) — потолок размера строки.
- Идентификаторы стабильные и уже есть: `protocolId`, `feedId`, `fetchedAt`, `updatedAt`.
